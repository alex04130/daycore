# API 契约的源文件

`api/openapi.yaml` 是**生成物**。要改契约，改这里，然后 `make api-bundle`。

```
head.yaml            openapi / info / servers / tags / security
paths/<tag>.yaml     路径条目，一个 tag 一个文件（18 个）
components.yaml      securitySchemes / responses / schemas
bundle/              合并器（Go，无新依赖）
```

## 为什么拆

一个 925 行的文件，计划里 **22 个工作项都要往它里面追加** —— 与 `server.go` 同一种争抢，但更狠一点：YAML 的合并冲突落在嵌套映射里面，只有能把整份文档记在脑子里的人才解得开，而解错了不会编译失败，只会让某个前端生成出错的类型。

拆完之后，改 plan 的人和改 admin 的人碰的是两个文件，**冲突从「必然」变成「只有真改同一个 tag 时才有」**。

## 三条规则（合并器会强制，不是约定）

1. **文件名就是 tag**，文件里每个操作的 `tags:` 必须等于文件名。不强制的话，第一个猜错的人之后「我这条路径该加到哪个文件」就又变成判断题了。
2. **`head.yaml` 的 `tags:` 列表是目录，也是合并顺序**。多一个没声明的 shard 会被静默漏掉 —— 路径在 git 里、契约里没有、没人报错，这是最坏的失败方式，所以两边的集合必须相等。
3. **顺序取声明顺序，不取文件名字母序**。字母序会把 `admin` 排到最前、把 `session`（入口）埋在中间。这个顺序同时是 Swagger UI 的分组顺序。

## 为什么是文本拼接而不是 YAML 重序列化

过一遍 YAML 库会丢掉全部 77 条注释，并且把每一行的格式重写一遍 —— 生成的文件既更难读，又**没法 review**（每次改动的 diff 都是整个文件）。拼接则让 shard 的字节原样出现在产物里。

代价是合并器不理解 YAML 结构（除了做上面三条校验时）。这个代价是对的：它的工作是拼接，不是理解。

## shard 为什么不带缩进

`paths/*.yaml` 里的路径条目在**第 0 列**，合并时由合并器统一缩进两格。这样每个 shard 自己就是一份能被编辑器解析的 YAML，而不是一段必须先想象它的上下文才能读的片段 —— 既然人是在 shard 里干活，那 shard 就该是好用的那一头。

（`$ref: '#/components/schemas/X'` 在单个 shard 里解析不了，只有产物能全量校验。编辑器的语法解析不受影响。）

## 过期会被抓住

`go test ./api/spec/bundle` 断言签入的 `api/openapi.yaml` 与 shard 一致。放在 `go test ./...` 里而不是只放 make 目标，因为提交前实际会跑的是前者 —— 而**契约过期是唯一没有别的症状的失败**：服务端是对的，shard 是对的，所有客户端读到的是一份两边都不符合的文件。
