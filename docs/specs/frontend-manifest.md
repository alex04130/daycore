# 前端 manifest 与主题协议（v1）

> 状态：**kind 体系 + 两层身份 + 握手已落地（2026-08-10，F7-A/B）**。
>
> 能用的：`internal/theme` 的三档 kind 体系与字符底线、`THEME_KINDS_DIR` 文件层、`frontend_families` / `frontend_builds` 两张表、`POST /api/version` 握手（token 空间取并集、kind 冲突报 409、rules 存而不用、运维的 family 归属不会被握手覆盖）。
>
> 还没有的：**按 family 的主题存储**（`custom_themes.family_id`，所以今天的主题仍然挂在那份写死的 13 条 token 上）、补算作业、以及控制台里那一屏（批准 rules、批准第三档 pattern、把 build 挪 family、钉住 family）。DB 层的 kind 也等那一屏。
>
> 给**写前端的人**看的 —— 包括第三方前端、以及同一系列的不同平台（琉璃可以有 web、app、嵌入式）。
>
> 设计裁决与理由在 [`docs/EXPERIENCE_CORE.md` §1.2](../EXPERIENCE_CORE.md)，这里是实现要照着做的那部分。

## 三条硬要求

任何前端 —— 包括第三方做的、别的平台的 —— 必须做到：

1. **握手并自我介绍**（`POST /api/version`）。不介绍，后端分不清连上来的是谁，主题与偏好就无处归属。
2. **首次安装配置界面**（`/setting` 或同等结构），至少能配**连哪个后端**。把后端地址写死的前端只能对着一个部署用，而自部署是这个项目的常态。这个界面同时是语言开关与主题选择的落点。
3. **自主丢弃用不到的主题 token**。主题按 family 存、token 空间取并集，所以你会拿到本 build 不认识的变量 —— 忽略它们是你的责任，后端不为此裁剪。

## 两层身份

| | 是什么 | 谁定 |
|---|---|---|
| **`buildHash`** | 一次构建的指纹（manifest 的哈希） | 派生，不可改 |
| **`familyId`** | 主题兼容组（如 `liuli`） | build 自己声明；**运维可在控制台改** |

主题、按端偏好、`ThemeSwitch` 全部按 **family** 存 —— 那才是一套主题有意义的单位。`buildHash` 让控制台看得见「琉璃 有三个 build 在连：web 4.2、app 1.0、嵌入式 0.9」，也让运维把一个新 build 归到已有 family。

## 握手

```
POST /api/version
  {
    "familyId":   "liuli",
    "buildHash":  "sha256:…",
    "displayName":"琉璃 · 长卷",
    "version":    "4.2.0",
    "minApi":     1,
    "theme": {
      "tokens": [
        {"name":"--primary",     "kind":"color",  "description":"主色（按钮/选中态）"},
        {"name":"--glass-blur",  "kind":"length", "description":"玻璃层模糊半径"},
        {"name":"--glass-alpha", "kind":"ratio",  "description":"玻璃层不透明度"}
      ],
      "builtins": [ {"id":"sky","name":"天空蓝","dark":false,"variables":{…}} ],
      "rules":    "琉璃的玻璃质感依赖 …（可选，见「rules 的处理」）"
    }
  }

  200 {
    "apiVersion": 1, "apiMinor": 0, "build":"2.3.0-beta", "channel":"beta",
    "minClient":  "…",
    "locales":    {"available":["en-US","zh-CN"],"defaultPrimary":"zh-CN","defaultSecondary":"en-US"},
    "assignedFamilyId":      "liuli",     // 运维可能改过，用这个，不要用你发的那个
    "rulesAccepted":         false,       // 未批准 → 后端用机械生成的规则
    "newTokens":             ["--glass-alpha"],
    "pendingThemeBackfill":  7            // 缺新 token 且**要花 AI 调用**的主题数（只数用户生成的）
  }
```

`pendingThemeBackfill` 只数用户生成的主题，因为默认主题取并集就补全了、不花钱（见下）。把两者加在一起报会让运维看到一个虚高的价钱，然后为了省这笔钱而推迟一件本来免费的事。

`buildHash` 一致就是空操作，所以每次启动调一次很便宜。`GET /api/version` 保持原样，给匿名与老客户端读。

## token 空间取并集，不做子集拦截

琉璃-app 用到的和琉璃-web 不必一致。

- **带来 family 没有的新 token** → family 的 token 空间扩一条。此时**已存的主题全都缺这一条**，运维在控制台跑一次**补算**：每个缺 token 的主题一次 AI 调用，按它现有配色补上。要花钱，所以是显式动作。
- **用不到 family 里的某些 token** → 不用管，**前端自己丢弃**。
- 补算后若两套主题变量完全一致 → **合并**，会话偏好改指。

### 默认主题不用补算 —— 所以早合并是免费的

**默认主题（build 自带的那几套）只取并集，不跑 AI。** 它们的值是前端作者写好随 manifest 报上来的，所以琉璃-web 的 `--rail-width` 和琉璃-app 的 `--safe-area-bottom` 各自都带着自己的值 —— 并起来就完整了，没有「缺一条要问模型补」这回事。

需要 AI 补算的只有**用户自己生成的主题**，因为只有它们没有作者能提供新 token 的值。于是补算成本有个很干脆的式子：

```
补算调用次数 = 缺新 token 的「用户生成主题」数量        （默认主题恒为 0）
```

**推论：一个 family 刚部署时合并是零成本的** —— 那时用户生成的主题还是 0 套。成本随用户攒主题单调增长，而且不会自己变小。

所以控制台在「把这个 build 归入某个 family」的入口旁边**报当下的价钱**，并且说明它只会变贵：

```
把 liuli-app 1.0 归入 family「琉璃」
  新增 token 3 个（--safe-area-bottom, --tab-bar-h, --haptic-scale）
  默认主题 5 套：并集即可，0 次调用
  用户主题 0 套：0 次调用
  ⓘ 现在合并不花钱。等用户攒了主题之后，每套缺 token 的主题要一次 AI 调用。
```

这条**不能反过来当成催**：拖着不合并是正当选择（还没想清楚两个端要不要共用主题），报价只是让「什么时候便宜」这件事不用自己猜。

控制台显示的是**差异**而不是通过／不通过：新增了哪几个 token、多少主题待补算、大约多少次调用。

## `kind`：任一时刻是封闭集合，但那个集合是数据不是代码

**先把两件被混在一起的事分开**（2026-07-29 修正，先前这一节把它们当成同一件）：

- 「**任一时刻只认已知的几种 kind**」—— 这条要守住，它是值层面注入面的钉子。
- 「**加一种 kind 要发一次后端**」—— 这条是先前那版的实现细节，不是安全要求，而且它错了。

这个仓库已经有现成的形状：**三层语言目录**（DB → `LOCALES_DIR/*.json` → 内嵌）让「加一门语言是丢一个翻译文件，不是改代码也不是发版」。`kind` 用同一个形状：`token_kinds` 表，文件作种子，内嵌那六种兜底。**加一种 kind 是插一行，不是切一个版本。**

### 为什么不是纯字符串

`kind` 主要不是用来管前端的，**它是给 AI 的类型签名**。没有它：

- 生成时模型没有靶子。`--radius-lg` 该给 `12px` 还是 `"cozy"`，只有 kind 说得清。
- **补算直接做不了**。「给这 37 套主题补上 `--tab-bar-h`」这句话要成立，前提是知道答案长什么样；不知道形状就只能整套重生成，那是另一个价钱，也会把用户调好的配色冲掉。
- `themeColorRe` 那条注释守的东西没了 —— 收窄的字符集是「通过变量值注入 CSS」不可能的原因。一个没校验的值里带 `url(https://…)`，用在会解析它的属性上就是一个信标。

所以纯字符串是拿这个功能的全部要点，去换一点灵活性 —— 而那点灵活性下面第二档已经给了。

### 三档，往下越自由，只有最后一档需要人点头

**第一档 · 原语**（封闭，但存在 DB／文件／内嵌三层里）

| `kind` | 值形状 | 例 |
|---|---|---|
| `color` | hex / `rgb()` / `rgba()` / `hsl()` / `hsla()` / `transparent` | `#f472b6` · `rgba(255,255,255,0.72)` |
| `length` | 数字 + 白名单单位（`px` `rem` `em` `ch` `vh` `vw`） | `12px` · `1.5rem` |
| `number` | 纯数字 | `1.6` |
| `ratio` | 0..1 | `0.75` |
| `duration` | 数字 + `ms`/`s` | `200ms` |
| `enum` | 前端列出字面允许值，后端只比对 | `blur` / `none` |

**第二档 · 组合子**（前端随便用，不需要批准）

```
one-of[blur, none, solid]      ← 就是 enum，写法更顺
list-of<length>                ← "0 2px 8px" 这类多值
nullable<color>                ← 允许显式「不设」
```

组合子**表达不出原语表达不了的东西** —— `list-of<length>` 的每一项还是过 `length` 校验器。所以它不需要门。多数「我需要一种新 kind」的真实需求落在这一档，一行代码不用改。

**第三档 · 前端自带 pattern**（要运维批准，与 `theme.rules` 同一道门）

manifest 里带 `{"kind":"pattern","pattern":"^clamp\\\\(…\\\\)$","examples":["clamp(1rem,2vw,2rem)"]}`。控制台显示 pattern、例子、以及**它会放进来但原语拦得住的字符**，运维批准后落进 `token_kinds`，从此它就是第一档的一员。

这一档负担得起的原因很具体：**Go 的 `regexp` 是 RE2 —— 线性时间、无回溯，构造不出灾难性回溯。** 所以一段被批准的第三方正则不会变成 DoS。（这也是为什么「前端自带正则」在别的语言里是坏主意、在这里不是。）

### 底线与 kind 无关

**不管什么 kind，任何值都还要过同一道字符底线**：不含 `url(`、`;`、`}`、`{`、`<`、`\`、`/*`、换行。

这一道是注入保证真正的落点。有了它，**保证不再依赖 kind 集合在代码里封闭** —— 一段写松了的第三档 pattern 最多是在一个安全字母表里面写松了，而不是开了个洞。先前那版把保证挂在「集合封闭在代码里」上，那才是「加 kind 要发版」的来源。

⚠️ **同名 token 在两个 build 里 kind 不同仍是真冲突**（`--accent` 一边 `color` 一边 `length`，主题就没意义了），控制台必须报出来让人处理。组合子不改变这条：`list-of<length>` 与 `length` 是两种 kind。

AI 生成的主题落地前**逐 token 校验**：key 必须在 family 的 token 空间里，value 必须过该 token 的 kind 校验器，再过上面那道字符底线。模型被诱导输出别的东西，进不了库。

## `rules` 的处理

`theme.rules` 是「怎么给这一端设计主题」那段提示词片段。

- 前端**可以**主动发一段。
- 运维在控制台**可以改它、决定是否采用**。
- **没有主张、或运维没同意 → 后端按 token 清单机械生成**（token 名 + kind + 描述），前端照样能用 AI 配主题，只是提示词是后端写的。

这个顺序是有意的：**未经批准的客户端文本不进 LLM，注入面默认为零。** 第三方前端一上来就能用完整功能，代价只是主题提示词平淡一点。响应里的 `rulesAccepted` 告诉你当前用的是哪一种。

⚠️ **前端是开放的** —— 第三方与多平台是一等场景，所以上报内容按第三方数据对待，不按「我们自己的代码」对待。`description` 同样有长度上限并去换行。

## 主题的读写

```
GET   /api/themes                 本 family 的内置 + 自定义主题
POST  /api/themes                 建一套自定义主题（variables 逐 token 校验）
POST  /api/ai/theme               自然语言 → 一套主题（走 theme_gen 提示词）
PATCH /api/session                {"currentTheme": "<themeId>"}  当前主题，按 family 分开
```

**当前主题按 family 分开存**（`SessionPrefs` 的 `{familyID: themeID}`）—— 桌面用琉璃、手机用汀 是常态。

## 没有传输规范，这是有意的

适配层是**后端调出去**，前端是**前端调进来**。所以这里没有子进程、没有 `format`、没有生命周期 —— 硬塞一段传输规范只会让人以为前端也要写成适配器。前端只需要一个 HTTP 客户端。

## 未定的口子

- **`builtins` 的更新语义**：新 build 改了某个内置主题的取值，已经选了它的用户看到的是旧值还是新值，未定。
- **family 的所有权**：第一个声明 `liuli` 的 build 定义它的 token 空间；运维 pin 之后才不可被覆盖。名字抢占的防护未定。

## 前端的多语言形态（2026-08-03 定）

后端这一侧已经是「**加一门语言 = 丢一个 JSON 文件**」：三层目录（DB 覆盖 → `LOCALES_DIR/<locale>.json` → 内嵌 zh-CN/en-US），不改代码不发版。**前端必须做成同一个形状**，否则这句话只对一半的产品成立。

现役 `web/frontend/src/i18n.js` 是一部硬编码的双语字典 —— 那正是**不要抄的**那一份。四端各抄一遍，就是把同一个错误复制四份。

### 四条要求

1. **文案与代码分离。** 语言包是数据文件，不是 `.js` 里的对象字面量。构建产物里能被替换、能被追加，不需要重新编译。
2. **可选语言从后端读，不要写死。** `GET /api/version` 的 `locales.available` 是**这个安装能渲染的全部语言**，不是编译期常量 —— 运维往 `LOCALES_DIR` 丢一个文件就会多一门，前端写死自己以为存在的那几种就会漏掉它。
3. **回退链与后端一致**：精确 → 同基础语言（`zh-TW` 先找 `zh-CN`）→ 默认 → 任意。最后一步是有意的：半翻译的界面显示读者可能不认识的语言，好过显示空白 —— **缺翻译是内容缺口，不是渲染故障**。
4. **缺 key 就显示 key 本身。** 不要显示空字符串（看起来像布局 bug），也不要现编一个（看起来像翻译错了）。

### 从哪拿翻译

后端的 `i18n.Export(locale)` 会给出**每一个 key 加上它当前的回退值** —— 那就是译者要填的那份文件。前端侧应当有等价物。

⚠️ **后端当前的 en-US 覆盖率是 97/338**（`TestReportCatalogCoverage` 会打印）。241 条未翻译的是错误文案，它们在这一批被从 Go 字面量搬进目录 —— **机制修好了，文案是另一件事**：写那 241 条英文属于文案定稿，而文案由项目规则冻结。今天 en-US 读者看到的中文与这一批之前完全一样，没有任何回归；区别是现在丢一个 JSON 文件就能翻掉它们。
