# 计划语义：锁、石化、提案

给**写前端的人**看，包括第三方与别的平台。这三样与本目录其余四份规范不同：它们不是「你的服务怎么接进来」，而是**你必须在自己这边算一遍、并且算得和后端一模一样**的东西。

后端始终是权威 —— 线上的每个块都带着算好的 `lockLevel`，每个提案都带着算好的 `state`。但前端要乐观构造：用户拖一个块、点一下完成、刚说完一句话就要看到结果，这些都发生在往返之前。所以同一个规则存在两份实现，而**两颗脑子迟早会不一致**。

对策不是「小心点」，是**共享夹具**：规则写成数据，两边把它当测试表跑。分歧是一次测试失败，不是生产里的一个惊喜。

| 语义 | 权威夹具 | 前端为什么要自己算 |
|---|---|---|
| 锁 | [`api/lock-rules.json`](../../api/lock-rules.json) | 用户新建一个块，要立刻知道它能不能拖 |
| 石化 / 相位 | [`api/testdata/petrify-vectors.json`](../../api/testdata/petrify-vectors.json) | 相位是**读时派生**，每帧都在变；问后端要就是每分钟一次请求 |
| 提案 | 见下，**尚无夹具** | 虚影要画在时间轴上、卡片要排进堆叠 |

> 本文件的状态：**锁与石化已实现且有夹具**；**提案的形状已定但契约夹具还没有**（见末节）。

## 一、锁：这个块能不能挪

三档，字符串枚举，`""` 表示**尚未派生**而不是「没有锁」—— 这个区别是承重的：用指针无法区分「键缺失」与「显式 null」，而设计原型里那是三态。

| `lockLevel` | 含义 | 拖动 |
|---|---|---|
| `hard` | 时间由外部决定（课表、会议） | 拒绝，给岔路而不是给错误 |
| `soft` | 有理由固定，但用户可以推翻 | 需要一次确认 |
| `none` | 自由 | 直接改 |
| `""` | 还没派生过 | 当 `none` 处理，但不要写回 |

`lockSource` 说这个档位是怎么来的：`derived`（按类型+标题推的，可以重算）/ `user` / `agent`（有人拍的，**永不重算** —— 否则手动解锁下次读就被锁回去）/ `""`（从未派生）。

**`lockReason` 的本地化**：`derived` 的理由是「档位」的一个渲染，所以**按读者的语言在出站时重新解析**（用户会切语言，写入时冻住的字符串会显示成另一种语言）。`user` / `agent` 写的理由**原样透传** —— 那是他自己的话，替他翻译是往他嘴里塞词。

**派生规则、正则、以及全部判定用例在 `api/lock-rules.json` 里**，包括那条 class-title 正则的逐字节原文（它来自设计原型的 JS，两边必须同一个模式串、同一个大小写不敏感标志、同一个 trim 行为）。照那份文件建一张测试表，不要照本文重新实现。

**⚠️ 锁守的是「什么时候」，不是「有没有」也不是「是什么」。** 两条默认理由自己写着 ——「课程**时间**由课表决定」/「Time you agreed with someone else」。所以：

| 动作 | 硬锁下 |
|---|---|
| 改 `time` / `date` / `duration_min` / `utc_time` / `time_mode` / `timezone` / `offset_*` | **拒绝** |
| `remove`（规则展开的块 → 墓碑，规则本身还在）= **请假** | 放行 |
| 改标题、打勾、加备注 | 放行 |

把锁读成「这一行只读」会关掉用户唯一的门：**请假走的正是 `remove`**，拦住它硬锁就成了一条没有出口的死路 —— 与锁存在的目的正好相反。写这道门的第一版就犯了这个错，实测才发现。

**⚠️ 锁拦的是用户，不是 agent。** `Movable(actor, confirmed)` 对 `agent` 与 `system` 一律放行：hard 锁表达的是「这个时间由课表决定，你自己改了也不会真的改变现实」，而 agent 重排与撤销回滚是系统在动自己的账。前端看到 AI 挪了一个 hard 块**不是 bug**，不要在本地拦下来 —— 拦了的结果是撤销回滚在你这一端悄悄失败。

`soft` 对用户需要 `confirmed=true`；`none` 与 `""` 直接放行。

### 409 信封（2026-08-03 落地）

锁与石化**共用一个 guard、一个 409 信封**。拒绝时返回：

```json
{
  "error": "blocked",
  "code": "locked" | "petrified",
  "message": "已本地化，可直接展示",
  "blockId": "…",
  "confirmable": false,
  "lockLevel": "hard",      // petrified 时不带
  "lockReason": "课表决定"   // petrified 时不带
}
```

**409 而不是 403**：调用方的身份没有任何问题，是请求与它所指的那个块的**状态**冲突，而状态会变 —— 软锁差一次确认，明天的块还没石化。403 是在告诉客户端别再问了。

**`confirmable` 只有软锁是 true**，因为软锁的出路真的存在：带 `action.confirm: true` 重发即可。硬锁与石化今天**没有出路**，信封如实说没有 —— 给一个没人兑现的按钮比给一个诚实的拒绝更糟。

### 三条岔路，现在有两条

| 岔路 | 怎么走 | 状态 |
|---|---|---|
| **请假（这次不去）** | `PATCH /api/plan` 的 `remove` —— 规则展开的块转墓碑，规则本身还在 | ✅ 一直可用，锁不拦它 |
| **解锁后再挪** | `POST /api/plan/lock` `{date, blockId, level:"none"}`，然后正常改时间 | ✅ 2026-08-03 |
| **标记冲突** | `POST /api/plan/conflict` `{date, blockId}` → 建一张决策卡 | ✅ 2026-08-03 |

**标记冲突不解决冲突，它把冲突变成一个决定。** 系统不知道两者哪个更重要，猜就是助手挪走用户在乎的那个的方式。所以它产出一张卡（三个选项：把另一件挪开 / 这次不去 / 都留着我自己看着办），由用户回答。

它**拒绝凭空造冲突**：真没有重叠就返回 422。一张声称「这两件撞了」而实际没撞的卡，会教会用户不信任所有的卡。

同一个冲突标两次是**一个问题不是两个**：已经在屏幕上的那张卡直接返回，不新建。这里不用 `Supersede` —— 它有意放过已投递的卡（不能把用户正在看的卡从他眼皮底下退休掉），而冲突卡一创建就是已投递。

`POST /api/plan/lock` 把 `lockSource` 置为 `user`，这正是 `lockSource` 存在的理由：不置的话，下一次写就会被派生重新锁上，解锁「活不过一次刷新」。解锁会**清空理由** —— 「课程时间由课表决定」不该继续挂在课表已经不管的东西上。

⚠️ **不提供「恢复成派生」**。「让规则重新说了算」与「我决定了」是两件不同的事，而目前没有任何设计要求前者 —— 在这里提供它等于凭空发明第三种状态让客户端去理解。

## 二、石化：过去什么时候变成记录

**线**：`min(now − horizon, 今天的日始)`，`horizon` 默认 5 小时（`GET /api/version` 之外的部署可改，夹具里带着 `horizonHours`）。

两半哪一半胜出就是全部设计：**白天日始胜出**，所以你正在过的这一天没有任何东西会当着你的面冻住；**过了午夜滚动窗口胜出**，所以凌晨一点你刚过完的那个晚上还是你的。到早上五点滚动窗口追上日始，昨天关闭。

**相位**（`PhaseAt`，检查顺序即语义）：

```
end   <  line  → stone   冻结：是记录不是计划
end   <= now   → recon   过去了，但还在可编辑窗口内
start <= now   → now     正在进行
否则            → future  还没开始
```

第一条是**严格小于**，后两条是**小于等于**。恰好落在线上的块还不是石头，恰好在此刻结束的块已经是 `recon` —— 这不是笔误，抄成一致的比较符会让边界上的块差一档。

顺序不能换：一个刚结束的块必须先被判成 `recon` 才轮到 `now`，否则「结束于此刻」会被读成「正在进行」。

### ⚠️ 日始不一定是午夜

这是本规范里最容易写错、也最容易在测试里看不见的一条。

**有一类时区在 00:00 换挡**（`America/Havana`、`America/Santiago` 每年都是），那天的本地午夜**不存在**。多数语言的日期构造在遇到不存在的墙钟时会做归一化，而**归一化的方向决定一切** —— Go 是向前回退，于是朴素的「取年月日、时分秒清零」返回的是**前一天 23:00**，一个不在自己那天里的「日始」。

三个后果，都实测过：石化线提前一小时；ask-first 卡片被封顶到一个过去的时刻，**出生即过期**（实测存活 −30 分钟）；「今天打过卡了吗」把前一晚 23:00 之后的算进今天。

`petrify-vectors.json` 的 `dst.midnightGap` 一节钉住这一类，**同时记录正确答案与朴素写法的错误答案**。后者不是凑数：只断言正确值的话，某台机器的 tzdata 恰好不同就会「碰巧通过」；断言错误值仍是那个错误值，才证明这个案例还活着。

要实现的三条不变量：

```
startOfDay(t) 落在与 t 相同的日历日
startOfDay(t) <= t < startOfNextDay(t)
22h <= startOfNextDay(t) − startOfDay(t) <= 26h
```

**不要用「加 24 小时」或「日期加一天」求次日日始** —— 两者都会被同一个空洞折回去。稳妥的锚点是**正午**：没有任何时区偏移过 ±12 小时，所以正午在每个日期上都存在。

### 另外两条 DST 行为

`petrify-vectors.json` 的 `dst.springForward` / `dst.fallBack` 记录的是墙钟解析：spring-forward 空洞**向前回退**（`02:30` → `01:30`），fall-back 歧义取**第一次**。这两条是被观测的行为而不是被推导的规则 —— 标准库自己把空洞情形写成「不保证」，所以观测值即契约。解析结果与后端不同的前端，会和后端在「这个块冻了没有」上分歧。

### 跨天块：一条数据，两天都算

**共识 25**：23:00 起两小时的块，昨天和今天的河里都有它。**数据一条**，两天渲染、两天算数 —— 选一天的结果要么把它从用户记得的那天藏起来，要么把它挪离它开始的那天。

所以 `GET /api/plan?date=D` 返回的块里会有**前一天外溢进来的**。它们带着**自己的 `date`**（前一天），这是识别它们的方式，也是必要的：一个没有 `date` 的外溢块会被按 D 解析时间，整整挪动二十四小时。

**外溢块是昨天那一行的一个视图，不要往它上面写。** 要改就带它自己的 `date` 去改，否则会造出第二行，"数据一条"那一半就没了。墓碑不外溢 —— 用户已经说了那次不算。

⚠️ 「越过午夜」用的是**下一天的日始**，不是「加 24 小时」。在午夜换挡的时区里这两者差一小时，见上一节。

### 重新安排（补钓）

**时间从来不是重点的那些事**（跑步、读书、跑腿）没做完可以给一个新时段；**预约不行** —— 错过的课就是错过了，再排一次是在骗人。判据在 `TimeBlock.Refishable()`：完成的、成就、`appointment`、已到上限的都不补。

**上限是反羞耻的那一半**。没有上限，系统会把同一件没做的事永远往前推，而那正是这个产品存在的意义所要避免的债务螺旋：诚实地问过几次之后，「你还没做这个」就不再是信息而是指责。

**链和计数由服务端算**，客户端只说「这是在补钓 X」：

- `rescheduled_from` 始终指向**根**，不是上一次尝试 —— 否则回答「那件事后来怎么了」要走一条链表。
- `reschedule_count` 由原块的计数 +1 得出，**不采信请求里的值**。采信的话，一个把自己计数清零的客户端就能让上限形同虚设。
- 找不到原块**不让写失败**：用户要加的那个块本身仍然想存在，所以丢掉那个声称、留下块。
- 到上限时返回 409，`code: "refish_capped"`。

## 三、提案：一个资源，四种看法

虚影、确认卡、决策卡、通道上的批准消息**是同一个对象**从不同端看过去的样子。待发池就是这张表 `state=pending` 的一个过滤。前端不该为它们建四个模型。

### 注意力阶梯

| `level` | 是什么 | 预算 |
|---|---|---|
| `L1` | 时间轴上的虚影，绑在一个时段上 | 无（在视野内，不打扰） |
| `L2` | 堆叠里的一张卡 | 同时 ≤3 张 |
| `L3` | 一次推送 | ≤3 条/天 |

`L0` 永远不会变成提案 —— 静默动作只进账本。

**⚠️ 「堆叠里有几张卡」是一个合取，不是问一个时间戳。** `deliveredAt` 是**永久戳**，从不清除，所以「投递过」数的是这个会话历史上被展示过的全部卡，包括早就接受、拒绝、过期的。拿它当堆叠预算，用户一生只能看到三张卡然后再也没有。真正的谓词是 `state=pending` **且** 投递过 **且** 仍可投递。

### TTL 不对称

这是产品的理论高峰之一，也是最容易做反的一条：

| `ttlPolicy` | 语义 | 做反的后果 |
|---|---|---|
| `silence_accepts` | **先斩后奏**：已经做了，沉默即确认 | 静默丢弃一个撤销窗口 |
| `silence_rejects` | **先奏后斩**：还没做，沉默即作废 | 无人看管地执行了工作 |

ask-first 的卡片**永不越过日界** —— 关于今天的提议不该明天还等在那里。封顶用的正是上一节那条日始（所以上一节那个空洞会让卡片出生即过期）。

### 状态：前端三态，服务端四态

契约里前端只需要认三种终态，但服务端有四种，因为**沉默的过期必须与明确的拒绝可区分**：账本记录一切（沉默也是一笔），而过期的提议用户从未见过。`expired` 因此不折进 `rejected`。

`resolution` 记录它是怎么离开 pending 的：`user`（明确答复）/ `silence`（TTL 到了）/ `superseded`（同 mergeKey 的新卡赢了）。

### 复合提案

一张卡里分行列出，**每行单独接受或拒绝**。行级接受走的是同一套乐观并发（`rev` 比对）—— 两个客户端接受同一张卡的不同行，如果不做比对，第二次写会抹掉第一次。

### 读与回答

| | |
|---|---|
| `GET /api/proposals` | **默认返回堆叠**：pending + 已投递 + 未过期。这个合取就是要点 —— `deliveredAt` 是永久戳，单问它会返回这个会话被展示过的全部卡 |
| `GET /api/proposals?all=1` | 控制台视角：这个会话有过的全部 |
| `POST /api/proposals/{id}/respond` | 回答一张**没人在等**的卡。空或 `reject` 是拒绝，其余按行接受 |
| `POST /api/decisions/{id}/respond` | 回答一张**正阻塞着 agent 回合**的卡。两者写同一行 |

**没被回答的卡是沉默不是拒绝。** 超时与取消都落 `expired` + `silence`：共识 15 要求「没人看过」与「说了不」可区分，而一张没被回答的卡从来没被看过。

### ⚠️ 这一节还没有夹具

锁和石化各有一份机器可读的判定表，提案没有。所以上面这些今天靠读文档实现，而**读文档实现的东西迟早会漂**。

冻结（批次 η）之前要补的是一份 `api/testdata/proposal-vectors.json`，至少覆盖：TTL 不对称的两条过期路径、日界封顶（含上面那个午夜空洞）、同 mergeKey 并列时谁存活、可投递集合排除过期与压后、以及堆叠谓词那个合取。

在那之前，**以 `internal/domain/proposal.go` 为准**，并且改它的时候要想着这一节。

## 四、给实现者的三条底线

1. **后端权威，前端乐观。** 你算出来的是为了不等往返，不是为了替代它。线上回来的值与你算的不一致时，以线上的为准并且**不要静默覆盖** —— 那说明两边的规则漂了，值得让人知道。
2. **跑夹具，别读散文重实现。** 本文解释为什么，`lock-rules.json` 与 `petrify-vectors.json` 定义是什么。冲突时以夹具为准。
3. **日界不是午夜。** 如果你的实现里出现「取年月日、时分秒清零」，它在一整类时区上是错的，而你的测试多半覆盖不到那类时区 —— 这个洞在本仓活了很久，正是因为原来的夹具只有一个 02:00 换挡的时区。
