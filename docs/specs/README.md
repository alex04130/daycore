# 规范目录

给**写适配器与写前端的人**看的协议文档，包括不是本项目成员的人。

与 `docs/` 里其余文档的分工：`docs/*.md` 是**实时项目文档**（这个仓库现在是什么样、为什么这样），`docs/specs/*.md` 是**对外契约**（别人要照着实现什么）。

| [storage-protocol.md](storage-protocol.md) | 第五种存储怎么接：8 个操作、**条件写为什么不能省**、没有条件写时的锁配方 | 定案，未实现（批次 F8b） |
| [provider-protocol.md](provider-protocol.md) | 天气 / 搜索 / 消息通道怎么接 | 定案，未实现（批次 F2） |

## 三份协议为什么共用一个 transport.md

子进程的握手与生命周期规则（那一行 stdout、`SIGTERM` 五秒、退出码与 stderr、重启退避、socket 谁删）在三份协议里**一字不差**。抄三遍的结果是它们迟早不一致，而不一致的规范比含糊的规范更糟 —— 实现者会照着其中一份写，然后在另一份的假设下被坑。

所以：**共同的部分写一次，各协议只写自己真正不同的那段握手载荷**（存储追加 `capabilities`、provider 追加 `manifest`）。

## 一条贯穿三份协议的规则

**客户端提供、要进 LLM 的文本，未经运维批准不使用。**

三处都有：provider 的 `manifest.description`（会进 companion 提示词列可用搜索源）、前端的 `theme.rules`（会进主题生成提示词）、以及将来任何适配层想给模型的自我描述。

处理一致：没有主张、或运维没批准 → 后端按结构化字段机械生成一段。第三方一上来功能完整，代价只是那段文字平淡；**注入面默认为零**，批准是「我读过这段文字」的显式动作。

这条不是洁癖 —— 前端与适配层都是**开放的**（第三方、多平台），所以上报内容按第三方数据对待，不按「我们自己的代码」对待。

## 前端 manifest 为什么没有传输规范

它的方向是反的：适配层是**后端调出去**，前端是**前端调进来**。所以前端 manifest 只是一个普通的 API 端点（`POST /api/version` 握手），没有子进程、没有 `format`、没有生命周期 —— 硬塞一段传输规范进去只会让人以为前端也要写成适配器。
